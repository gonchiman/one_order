# プロジェクトの目的と実装方針

このプロジェクトの作業開始時に読む。

## 目的と優先順位

- ONE ORDERは、TypeScript・Phaser・Viteで開発する盤上ゲーム。まずは盤上で駒を動かし、操作とゲームの進行を検証できる状態を目指す。
- ゲームデザインの検証を先に進め、グラフィックデザインは後の工程に分ける。
- 学習機能は後の工程とする。学習環境、訓練処理、外部AIとの接続などを依頼範囲に含まれていない段階で追加しない。
- 未決のゲームルールを確定仕様として扱わない。試作用の仮ルールを追加する場合は仮定として明示し、後から変更できるようにする。

## 試作時の表示

- 最初の参考画像を見た目の基準にしない。
- 白地と標準文字を基本とし、盤面や操作にはマス目・記号・数値・標準的な操作部品を使う。ルールと操作を確かめるために必要な表示に絞る。
- 色分けは陣営や選択状態などの識別が必要な場合に限る。装飾、ピクセルアート、世界観に合わせた素材や演出は後から検討する。
- UI内の文章は、UIを扱う際に [UIの補足テキスト方針](ui-text.md) に従う。

## 実装の基本方針

- 盤面状態、指示、移動、戦闘、ターン進行などのゲームルールは、PhaserやDOMに依存しないTypeScriptとして扱う。Phaserのシーンは表示と入力を担当する。
- 描画やアニメーションの都合でゲームルールを決めない。ルールの計算結果を表示へ渡し、表示を差し替えてもルールを検証できる構成にする。
- 状態やルールの定義を複数箇所へ複製しない。新しい機能は既存の型・処理を確認し、必要な範囲で追加・拡張する。
- 将来の学習導入や別エンジンへの移行のために、使い道が決まっていない大規模な抽象化を先回りで追加しない。

## 変更時の確認

- コードやビルド設定を変更した場合は `npm run build` で型チェックとビルドを確認する。
- ゲームルールを追加・変更した場合は、状態遷移や境界条件など、振る舞いの正しさを確認できるテストを実行する。テストがないことをテスト済みと報告しない。
- 表示や入力を変更した場合は、ブラウザーで該当する操作と表示を確認する。
- 指示・文書のみの変更では、内容、参照先、適用範囲、矛盾や重複を確認する。ゲームのビルドやテストを形式的に追加実行しない。

## 指示・仕様と実装の区別

- 指示・仕様を保存しただけで、対応する機能や共通部品が実装済みであると扱わない。
- 相談や案の提示だけの依頼を、アプリ実装の開始指示として扱わない。実装、学習、自動化、公開は、その作業の依頼範囲に応じて行う。
